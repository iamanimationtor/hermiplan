# گزارش ممیزی، اصلاح و ارتقای HERMIPLAN

مبنا: مأموریت «ممیزی جامع، اصلاح و ارتقای فنی HERMIPLAN» — مخزن `iamanimationtor/hermiplan`، شاخه
`arena/2f8571d5-hermiplan`.

> **وضعیت فاز:** گزارش پیشرفت ارائه‌شده؛ تأیید نهایی در انتظار بررسی شواهد.
> جدول تطبیق کامل معیارهای مأموریت در [`docs/PROMPT-COMPLIANCE.md`](PROMPT-COMPLIANCE.md) و
> خروجی خام آزمون‌ها در [`docs/evidence/`](evidence/) قرار دارد.

این گزارش **فقط کارهای انجام‌شده و آزمون‌های واقعاً اجراشده** را ثبت می‌کند. هر جا کاری انجام
نشده یا آزمونی اجرا نشده، در همان بخش با صراحت نوشته شده است. هیچ آزمونی «فرضی موفق» ثبت نشده.

## ۲. تغییرات معماری

1. **لایه‌بندی صریح**: `lib/engine` (محاسبه خالص، بدون React و بدون I/O) ← `lib/market`
   (نرخ/هزینه) ← `lib/report` (تولید خروجی) ← `app/api` (فقط اعتبارسنجی، احراز هویت، محدودیت
   نرخ، قالب پاسخ). هیچ محاسبه‌ای در کامپوننت انجام نمی‌شود.
2. **یک مسیر واحد برای ورودی عددی**: `normalize-input.ts` + اسکیمای Zod ⇒ گرد کردن و کلمپ
   فقط یک‌بار، بنابراین «نمایش» و «محاسبه» همیشه هم‌خوان‌اند.
3. **یک مسیر واحد برای تاریخ→موقعیت**: `resolveDatePosition` در `calendar.ts` برای تاریخ
   وضعیت/مهلت/محدودیت‌ها، با تشخیص‌های صریح.
4. **تشخیص‌های ساختاریافته**: `Diagnostic { kind, severity, code, activityIds, message }` جای
   رشته‌های پراکنده؛ `kind` مقوله را مشخص می‌کند (داده، چرخه، منطق شبکه، محدودیت، تقویم، ظرفیت)
   و `status` تحلیل از همین‌ها مشتق می‌شود (`valid/warning/inconsistent/invalid/internal-error`).
5. **یک تصویر از نرخ‌ها**: `MarketSnapshot` از گرفتن تا اعمال؛ آنچه کاربر می‌بیند همان چیزی است
   که اعمال می‌شود؛ ردیف‌های نامعتبر قرنطینه و `feedError` گزارش می‌شود.
6. **حریم خصوصی به‌صورت پیش‌فرض**: پروژه/profile موجودیت مالک دارد، گزارش خصوصی است و مسیر
   مشاهده اشتراکی فقط با توکن ۲۵۶ بیتی (فقط هش در پایگاه داده) باز می‌شود؛ UUID مجوز نیست و
   ساخت/ابطال/مصرف لینک در `project_events` ثبت می‌شود.
7. **لایه سرویس سرور** (`lib/server`): `auth`, `otp`, `sms`, `rate-limit`, `http`, `share-token`,
   `project-versions` — قابل آزمون جدا از مسیرهای Next.
8. **تاریخچه نسخه و ویرایش هم‌زمان**: ردیف زنده (`projects.input`) منبع حقیقت می‌ماند و هر تغییر
   پذیرفته‌شده یک نسخه‌ی تغییرناپذیر در `project_versions` می‌گذارد. شماره نسخه (`projects.version`)
   توکن هم‌زمانی است: کلاینت شماره‌ای را که از آن ویرایش کرده می‌فرستد و اگر عقب‌تر باشد **۴۰۹**
   می‌گیرد، پس دو تب/دو دستگاه نمی‌توانند نوشته‌ی هم را بی‌صدا پاک کنند. بازگردانی هم یک تغییر
   است: ابتدا وضعیت فعلی (`pre-restore`) و سپس وضعیت بازگردانی‌شده (`restore`) ثبت می‌شود.
9. **تصمیم بر پایه‌ی دیده‌ها، نه حدس**: `lib/report/version-diff.ts` دو نسخه را معنایی مقایسه
   می‌کند (فعالیت/منبع/ریسک/نقطه عطف/خط مبنا/تنظیمات) و هیچ فیلدی را نادیده نمی‌گیرد؛ فیلد
   ناشناخته با نام خام خودش گزارش می‌شود. تابع خالص است، پس با ۴۱ بررسی مستقل آزموده می‌شود و
   پاسخش در هر اجرا یکسان است. مسیر `…/versions/:n/diff` هم فقط برای مالک باز است.
10. **حالت دسترسی به‌عنوان یک تصمیم متمرکز**: محدودیت‌های محصول (سهمیهٔ ساخت/تحلیل/خروجی/لینک،
   سقف لینک فعال، اندازهٔ تاریخچه) در `src/lib/access-mode.ts` به یک پروفایل تبدیل شده‌اند و
   فایل `config/access.json` تنها جایی است که حالت را تعیین می‌کند (`open` برای دوران
   پیش از انتشار، `locked` برای سهمیه‌های کامل). پروفایل یک تابع خالص است، پس قواعدش بدون
   سرور آزموده می‌شود؛ لایهٔ سرور فقط آن را می‌خواند و `/api/health` حالت فعال و منبعش را
   اعلام می‌کند. هیچ مسیر دیگری عدد سهمیه را مستقیم در خود ندارد.

### مراحل استقرار (Netlify + PostgreSQL)

1. مخزن را به Netlify وصل کنید؛ `netlify.toml` (build = `npm run build`) و `.nvmrc` (22) موجود است.
2. `DATABASE_URL` را با scope **Functions** تنظیم کنید (endpoint تجمیعی توصیه می‌شود).
3. مهاجرت را **دستی و یک‌بار** اجرا کنید: `npm run db:status` سپس `npm run db:migrate`
   (پیش از آن `pg_dump`). این کار در بیلد انجام نمی‌شود.
4. پس از استقرار: `curl /api/health` باید `ok:true` و `schemaVersion` جاری را برگرداند
   (در نبود مهاجرت ۵۰۳ + `missingTables` می‌دهد).
5. پیش از اطلاع‌رسانی انتشار: `npm run db:share-audit` را اجرا و پروژه‌های «لینک قدیمی»
   (منتشرشده پیش از `0003`) را فهرست کنید؛ لینک UUID قدیمی آن‌ها دیگر کار نمی‌کند و باید
   لینک تازه صادر شود.
6. **Rollback کد:** Deploys → last known-good → Publish. **Rollback پایگاه:**
   جدیدترین اول: `0004_project_versions.rollback.sql` (تاریخچه را پاک می‌کند؛ پیش از اجرا مطمئن
   شوید نسخه‌های لازم را نگه داشته‌اید)، سپس `0003_share_tokens.rollback.sql` و
   `0002_security_hardening.rollback.sql`؛ در پایان حذف ردیف‌های متناظر از
   `_hermiplan_migrations`. اگر داده باید سالم بماند، بازگردانی بکاپ مقدم است.
   **توجه:** پس از اجرای rollback کد به نسخه‌ی پیش از تاریخچه، جدول `project_versions` بی‌مصرف
   ولی بی‌خطر است؛ کد قدیمی آن را نمی‌خواند.

جزئیات کامل در `DEPLOYMENT.md` (بازنویسی‌شده در این بسته).

## ۷. پیشنهاد فاز بعد (به ترتیب اولویت)

1. **برنامه ارتباطی لینک‌های قدیمی** (تنها کار باقی‌مانده اشتراک): پیش از انتشار، `db:share-audit`
   اجرا و فهرست پروژه‌های «منتشرشده پیش از ۰۰۰۳» به مالکان اطلاع داده شود تا لینک تازه بسازند.
2. **تثبیت آزمون PostgreSQL در CI**: سرویس `postgres:17` در pipeline و اجرای
   `npm run db:migrate && npm run test:api && npm run test:db:integrity` تا نسخه‌های ۱۵/۱۶/۱۷ و
   pooler میزبان هم پوشش داده شود (امروز روی ۱۸٫۶ محلی سنجیده شده است).
3. **آزمون بصری خودکار (Playwright)** برای موبایل/دسکتاپ و چاپ A4 — تنها شکاف آزمونی شناخته‌شده.
4. **مهاجرت به OTP مبتنی بر پروفایل مشتری** با پشتیبانی چند ارائه‌دهنده و لاگ تحویل (وضعیت
   ارسال/تحویل) تا «پیامک ارسال شد» قابل اثبات باشد.
5. **مدل چندشرکتی**: `Company`/`CompanyMember`/`ProjectMember`/`Role` فقط زمانی که نیاز محصولی
   روشن شد؛ طراحی پیشنهادی: نقش‌ها در سطح پروژه با جدول واسط و مجوزهای ریزدانه.
6. **پیوند به فهرست‌بها**: ورود داده رسمی فقط با سند و امضای دیجیتال؛ تا آن زمان ارجاع
   «مرجع/برآوردی» حفظ شود.
7. **EVM پیشرفته**: EAC وزنی (BAC/CPI و فرمول‌های ETC مستقل) به‌عنوان گزینه قابل انتخاب با
   مستندسازی، و ثبت تاریخ‌دار هزینه‌های واقعی برای `costDataCoverage=100٪`.
